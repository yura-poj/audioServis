# Аудиосервис

Домашний сервер для личных медиатек MP3. Клиенты для macOS 14+ и Android 8+ умеют перемешивать всю медиатеку, воспроизводить выбранный плейлист и скачивать трек при лайке. Раздел «Скачанные» работает при недоступном сервере. На Android очередь продолжает играть после блокировки экрана.

Чтобы перемотать текущий трек, нажмите на шкалу времени внизу плеера или перетащите ползунок к нужному моменту. Перемотка работает и на паузе, и в разделе «Скачанные».

Откройте меню с именем аккаунта → «Настройки» → «Скачивать понравившиеся треки на это устройство». По умолчанию автоскачивание включено. Выбор запоминается отдельно для каждого аккаунта на каждом устройстве. Он действует на новые лайки. Уже скачанная музыка остаётся доступной офлайн.

## Сервер

Понадобятся Go 1.26 и PostgreSQL 18. Подготовьте отдельную базу и роль, которой принадлежат объекты схемы сервиса. Передайте строку подключения в переменной `AUDIOSERVICE_DATABASE_URL`. Для сетевого подключения к PostgreSQL настройте TLS согласно конфигурации сервера базы.

```sh
go build -o dist/audioservice ./cmd/audioservice
export AUDIOSERVICE_DATABASE_URL='postgres://audio:password@127.0.0.1:5432/audio?sslmode=disable'
dist/audioservice migrate
dist/audioservice user create --name 'Мой аккаунт'
dist/audioservice serve --data-dir ./data
```

Замените значения в примере на реквизиты вашей локальной базы. `user create` печатает личный ключ. В приложении укажите адрес и ключ своего аккаунта. Повторите создание аккаунта для каждого слушателя.

По умолчанию сервер доступен на Mac по `http://localhost:8080`. Для Android-эмулятора или подключённого по USB Android используйте `adb reverse tcp:8080 tcp:8080` и тот же адрес в приложении.

### Домашняя сеть

Настройте сертификат с SAN для имени или IP, по которому клиенты будут обращаться к серверу. Передайте PEM-файлы цепочки и закрытого ключа.

```sh
dist/audioservice serve --listen 0.0.0.0:8080 --data-dir ./data \
  --tls-cert /path/to/fullchain.pem --tls-key /path/to/key.pem
```

Введите в приложении `https://<имя-или-IP>:8080`. Для собственного центра сертификации установите доверенный корневой сертификат на клиентских устройствах. На macOS разрешите приложению доступ к локальной сети, если система покажет запрос.

Для резервной копии остановите сервис и сохраните согласованные снимки PostgreSQL и каталога `data/audio`. При восстановлении используйте каталог аудио и копию базы с одного момента времени.

## Сборка клиентов

На macOS запускайте сборку из корня репозитория с установленными Command Line Tools.

```sh
./macos/build-app.sh
open dist/AudioService.app
```

Для Android укажите JDK 17 и каталог Android SDK с платформой API 36 и Build Tools 35.0.0.

```sh
export JAVA_HOME='/path/to/jdk-17'
export ANDROID_HOME='/path/to/android-sdk'
./android/gradlew -p android :app:lint :app:assembleDebug
adb install android/app/build/outputs/apk/debug/app-debug.apk
```

APK подписывается локальным debug-ключом. Для обновления установленного APK используйте тот же ключ подписи.

## API

Все маршруты находятся под `/api/v1`. Для запросов используйте заголовок `Authorization: Bearer <ключ>`. Списки возвращаются в поле `items`.

```sh
# URL сервера и личный ключ уже заданы в AUDIO_BASE и AUDIO_KEY.
curl --fail-with-body "$AUDIO_BASE/api/v1/playlists" \
  -H "Authorization: Bearer $AUDIO_KEY" \
  -H 'Content-Type: application/json' \
  --data '{"name":"Дорога"}'

# PLAYLIST_ID содержит id из ответа. Параметр playlist_id можно опустить.
curl --fail-with-body "$AUDIO_BASE/api/v1/tracks?title=Demo&playlist_id=$PLAYLIST_ID" \
  -H "Authorization: Bearer $AUDIO_KEY" \
  -H 'Content-Type: audio/mpeg' \
  --data-binary @song.mp3
```

- `GET /me` возвращает текущий аккаунт.
- `GET /playlists` и `POST /playlists` читают список и создают плейлист. `PATCH /playlists/{id}` меняет `name`, `DELETE /playlists/{id}` удаляет плейлист.
- `GET /playlists/{id}/tracks` возвращает треки в порядке добавления. `PUT` и `DELETE /playlists/{id}/tracks/{track_id}` добавляют и убирают связь с существующим треком.
- `GET /tracks` возвращает личную медиатеку. `POST /tracks` принимает MP3 до 64 МиБ включительно. Сервер проверяет кадры MPEG-1/2/2.5 Layer III, поддерживает CBR, VBR, начальный ID3v2.2–2.4 и конечный ID3v1. Повреждённая структура, free-format и посторонние данные между кадрами или в конце приводят к ответу `422 invalid_mp3`. `PATCH /tracks/{id}` меняет `title`, `DELETE /tracks/{id}` удаляет трек и его связи.
- `PUT /tracks/{id}/like` ставит лайк, `DELETE /tracks/{id}/like` снимает. При включённом автоскачивании клиент сохраняет MP3 на устройстве, где поставили лайк.
- `GET /media/{track_id}` отдаёт MP3 и поддерживает `Range`. `HEAD` возвращает заголовки файла.

Трек можно включить в несколько плейлистов. Удаление из плейлиста сохраняет его в медиатеке. Сохранённую локальную копию можно удалить отдельно в «Скачанных».

## История прослушивания

Обновите сервер, выполните `audioservice migrate` и запустите новые клиенты. Запись истории начинается с первого воспроизведения в обновлённом клиенте. Каждый запрос истории требует личный ключ владельца медиатеки.

- `GET /api/v1/history?limit=100` возвращает `items` в порядке убывания времени старта и `next_cursor`. Для следующей страницы передайте полученное значение в `cursor`. Диапазон `limit` от 1 до 500, по умолчанию 100. При поздней доставке офлайн-прослушиваний перечитайте нужный период.
- `GET /api/v1/tracks/{track_id}/listening-stats` возвращает `track_id`, `starts` (сколько раз трек начал играть), `completions` (сколько раз он достиг естественного конца) и `listened_ms` (сумма времени воспроизведения). Пауза, буферизация и расстояние перемотки в эту сумму не входят. Возобновление после паузы продолжает тот же запуск.
- `PUT /api/v1/history/{play_id}` принимает снимок одного запуска. Клиент создаёт UUID при фактическом начале музыки и передаёт тот же ID для последующих обновлений. Успех возвращает `204`. Повторная отправка безопасна. Повторное использование ID с другими исходными данными или занятого номера в той же очереди возвращает `409 play_conflict`. После удаления трека сервер удаляет его историю и возвращает для отложенной записи `404 track_not_found`.

Так выглядит тело PUT для трека, который пропустили через 12 секунд.

```json
{
  "track_id": "b74655e1-e57b-4c32-b326-bd0f94cbcf74",
  "queue_id": "734ef3b7-2099-4b4d-9490-8db120baaac1",
  "sequence": 1,
  "previous_play_id": null,
  "started_at": "2026-11-25T06:00:00.000Z",
  "listened_ms": 12000,
  "duration_ms": 60000,
  "start_reason": "selection",
  "outcome": "skipped"
}
```

`started_at` относится к началу музыки на устройстве. `duration_ms` – длительность записи, если плеер уже её определил. `queue_id` и `sequence` позволяют восстановить порядок на одном устройстве при одновременном прослушивании с нескольких. `previous_play_id` указывает на предыдущий фактический запуск в этом плеере, в том числе при ручной замене очереди. После перезапуска приложения или смены профиля связь начинается заново.

`start_reason` принимает значения `selection` (выбор трека), `queue` (запуск списка), `shuffle`, `skip` (ручное переключение) и `automatic`. Возможные исходы – `in_progress`, `completed`, `skipped`, `stopped`, `error`, `interrupted`. На счётчик завершений влияет только `completed`. Достижение конца после перемотки также даёт одно завершение.

Клиент сохраняет прослушивание локально при смене состояния и примерно каждые 5 секунд, пока музыка играет. Статистика API отражает последнюю доставленную длительность. После восстановления связи открытый клиент отправляет накопленное под исходным аккаунтом. При аварийном закрытии последний сохранённый интервал восстанавливается с исходом `interrupted` при следующем входе в этот профиль.

## Моя волна

В медиатеке Android или macOS нажмите «Моя волна». Если песня уже играет, она доиграет с текущей позиции. Сервер подбирает продолжение из вашего каталога по сходству звучания и всей синхронизированной истории с полуночи по времени сервера. Волна учитывает дослушивания и быстрые пропуски. Она заканчивается, когда треки исчерпаны. Выбор обычной очереди завершает волну.

Серверу нужен один фоновый анализатор. Установите модель Discogs-EffNet multi v1 и CPU runtime до запуска миграции и сервера. Пример для Python 3.11 и macOS arm64:

```sh
python3.11 -m venv .wave-env
.wave-env/bin/pip install -r internal/media/embedding/requirements.txt
mkdir -p data/models
curl -fL https://essentia.upf.edu/models/feature-extractors/discogs-effnet/discogs_multi_embeddings-effnet-bs64-1.onnx -o data/models/discogs_multi_embeddings-effnet-bs64-1.onnx
export AUDIOSERVICE_WAVE_MODEL="$PWD/data/models/discogs_multi_embeddings-effnet-bs64-1.onnx"
export AUDIOSERVICE_WAVE_PYTHON="$PWD/.wave-env/bin/python"
```

SHA-256 весов: `65cfde30655a939de420e5c09a49a43648336fdbbf79eb3af6d3b40176339d8e`. При обновлении остановите старый сервер, выполните штатную миграцию и запустите новую версию. Фоновые задания для существующих MP3 создаются миграцией, для новых – при загрузке. Обработчик обслуживает по одному файлу, хранит один вектор на запись и продолжает незавершённую обработку после перезапуска. Все вычисления выполняются на сервере. [Описание модели и условия использования](https://essentia.upf.edu/models.html#discogs-effnet)

Авторизованный запрос `POST /api/v1/wave/next` принимает `current_track_id` (UUID или null) и `excluded_track_ids` (ID уже выбранных песен). Ответ 200 содержит трек, 204 означает конец волны, 409 означает ожидание анализа, 422 сообщает об ошибке анализа.
